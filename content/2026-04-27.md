## Core Concept 1 — Coordinator vs Sub-agent
### Coordinator の仕事
- 問題全体を把握する
- タスクを適切に分解する
- 誰に何を任せるか決める
- 結果を統合する
- 必要なら追加の質問や再委譲を行う

### Sub-agent の仕事
- 狭い責務に集中する
- 与えられた目的に対して専門的な処理を行う
- 自分の担当範囲の結果を返す
- 全体方針は決めない

### One-line mental model
- coordinator = 監督・分配・統合
- sub-agent = 専門担当

## Core Concept 2 — When to Split into Sub-agents
以下の条件があると分割の価値が高い。

### Split when...
1. **責務が明確に分かれる**
   - 例: 調査 / 要約 / 検証

2. **並列化で効率が上がる**
   - 例: 複数ソース調査を同時に行う

3. **コンテキストを分離したほうが良い**
   - 例: 法務確認と技術調査を別にする

4. **専門性が異なる**
   - 例: コードレビュー担当とセキュリティ担当

5. **失敗点を切り分けやすくしたい**
   - 例: どの段階が壊れたか追えるようにする

## Core Concept 3 — When NOT to Split
複数 agent にすれば常に良いわけじゃない。

### Do not split when...
1. **タスクが単純で短い**
   - 1 agent で十分なら分割はオーバーヘッド

2. **各 agent に渡す文脈がほぼ同じ**
   - 分けても context handoff のコストだけ増える

3. **分割境界が曖昧**
   - 誰が何を担当するか不明だと失敗しやすい

4. **統合コストが高い**
   - 最後に結果をマージする手間が大きい

5. **責務の分割より tool 設計改善の方が先**
   - agent を増やす前に、tool の責務を見直すべきケースも多い

## Context Handoff Basics
sub-agent に渡す文脈が雑だと、全体設計はすぐ崩れる。

### Good handoff includes
- 何を達成してほしいか
- どこまでが担当範囲か
- 使ってよい tool は何か
- 返してほしい出力形式は何か
- 前提事実と制約条件

### Bad handoff examples
- 「調べて」だけ渡す
- 前提となる制約を渡さない
- 返却形式を指定しない
- 成功条件が曖昧

## Architecture Anti-patterns
今日は最低 3 つ書ければ OK。候補はこれ。

### Anti-pattern 1 — Everything agent
1つの agent に、調査・判断・実行・整形・例外対応を全部載せる。

なぜ悪いか:
- 責務が重すぎる
- 失敗時の原因が見えにくい
- context が膨らみやすい

### Anti-pattern 2 — Over-delegation
細かすぎる sub-agent に分解しすぎる。

なぜ悪いか:
- handoff コストが大きい
- 統合が複雑になる
- 実質的な価値が増えていない

### Anti-pattern 3 — Blind delegation
sub-agent に十分な context や成功条件を渡さず委譲する。

なぜ悪いか:
- 結果の品質が不安定
- 無駄な往復が増える
- coordinator の責任放棄になる

### Anti-pattern 4 — No failure surfacing
sub-agent の失敗を曖昧に握りつぶす。

なぜ悪いか:
- 信頼性が落ちる
- 最終出力の根拠が弱くなる
- human escalation の判断ができない

### Anti-pattern 5 — Wrong specialist boundary
役割分担が機能単位ではなく、なんとなく分けられている。

なぜ悪いか:
- 境界が曖昧
- 依存関係が増える
- 再利用しにくい
