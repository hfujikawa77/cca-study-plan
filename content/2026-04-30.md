# Domain 4 — Prompt Engineering and Structured Output

## Core Concept 1 — Structured Output
### なぜ structured output が必要か
AI の出力は自然文になりがち。
しかし実システムに組み込む場合、後続の処理が出力の形式に依存する。

例:
- JSON を受け取って DB に書き込む処理
- 特定フィールドだけ取り出して次の tool に渡す処理
- 複数 agent の出力を統合する処理

これらは、出力形式が安定していないと壊れる。

### Structured output の実現手段
1. **Prompt で指示する**
   - 「以下の JSON 形式で返してください」と明示する
   - シンプルだが、Claude が逸脱することがある

2. **JSON schema で強制する**
   - 期待する出力の型と構造を schema で定義する
   - 遵守率が上がる

3. **Validation で確認する**
   - 受け取った出力が期待形式かチェックする
   - 不正なら retry or fallback

### One-line mental model
Structured output = 「後続処理が使える形で出力させる」設計

## Core Concept 2 — Prompt Engineering Principles
試験で問われる基本的な原則。

### 明確なタスク定義
- 何をしてほしいか、何をしてほしくないかを明示する
- 曖昧な指示は曖昧な出力を生む

### 具体的な出力形式の指定
- 出力が何行か、どの形式か、何を含めるかを指定する
- 例: 「3 行で要約してください、箇条書きで、各項目は 20 字以内」

### 文脈の提供
- Claude が判断するために必要な情報を渡す
- 必要最小限に絞る（不要な情報は判断を歪める）

### Few-shot examples
- 期待する出力の例を 1〜3 個含めると品質が上がる
- 良い例と悪い例の両方を見せる効果もある

### Prompt のアンチパターン
- 複数の異なるタスクを 1 プロンプトに詰め込む
- 矛盾する指示を入れる
- 形式指定なしで構造化データを求める
- 出力例なしで複雑なフォーマットを要求する

# Domain 5 — Context Management and Reliability

## Core Concept 3 — Context Management
Claude の context window は有限。
長い会話やドキュメントを扱うとき、何を保持して何を捨てるかが設計の要になる。

### Context management の主要戦略

1. **Summarization（要約）**
   - 古い会話ターンや長いドキュメントを要約して文字数を圧縮する
   - 詳細は失われるが、全体の流れは保てる

2. **Selective inclusion（選択的な組み込み）**
   - 現在のタスクに必要な情報だけを context に入れる
   - 不要な情報は context に含めない

3. **External memory（外部記憶）**
   - 長期的に保持したい情報は外部ストレージ（DB, ファイル）に保存する
   - 必要なときだけ取り出して context に追加する

4. **Scratchpad / Working memory**
   - agent が中間結果を書き出す場所を用意する
   - context を使い切る前に中間状態を記録できる

### Context management のアンチパターン
- context を何も管理せず、どんどん積み上げる
- 古い・無関係な情報を context に残し続ける
- context が不足してもエラーにせず暗黙に失敗する

## Core Concept 4 — Reliability: Validation / Retry / Escalation
信頼性設計の 3 本柱。試験で頻出。

### Validation（検証）
- 入力と出力が期待通りかを確認する
- いつやるか: tool の入力前、tool の出力受け取り後、最終結果の前

### Retry（再試行）
- 一時的なエラーに対して、再度実行する
- ルール: 一時的エラーにのみ使う、回数に上限を設ける、バックオフを入れる
- やってはいけないこと: 永続エラーに retry する、無限 retry する

### Escalation（人間への引き渡し）
- 自動処理では解決できないとき、人間に判断を求める
- いつやるか: retry 上限を超えたとき、権限が不足しているとき、判断が曖昧なとき

### 3つの関係
```
入力 → Validation → 実行 → Validation → 出力
                         ↓エラー時
                      Retry (一時的なら)
                         ↓上限超え or 永続エラー
                      Escalation
```

### 信頼性設計のアンチパターン
- validation なしで tool を実行する
- エラーを検知しても retry もせず無視する
- 自動化できないケースを想定せず、escalation の仕組みを作らない
- retry に上限を設けず無限に回す

## Cross-Domain Review: Domain 4 + 5 Connection
Domain 4 と 5 は切り離せない。

| Domain 4 | Domain 5 |
|---|---|
| 出力形式を指定する | 出力を validation する |
| prompt で期待値を伝える | retry で品質を安定させる |
| few-shot で期待を示す | escalation で人間に判断させる |

「良い prompt を書いても、validation がなければ信頼できない」
「validation があっても、retry / escalation がなければ壊れたとき対処できない」
